# 2026-08-10 — issues 56, 66, 69 fixed (Liquid Memories zero-cost, Omamori underflow, Smoke Bomb no-op)

Date: 2026-08-10
Session/task: Investigator-audit bug-fix pass on `src/combat/BattleContext.cpp`

## Decision

- **Issue 56 (Liquid Memories zero-cost):** `BattleContext::chooseDiscardToHandCard`
  now honors its `forZeroCost` parameter instead of the never-reset
  `cardSelectInfo.cardSelectTask == CardSelectTask::LIQUID_MEMORIES_POTION`
  test. All call sites already pass the correct flag
  (`Actions.cpp::BetterDiscardPileToHandAction` passes
  `task==LIQUID_MEMORIES_POTION`; `search::Action::execute` passes true for
  LIQUID_MEMORIES_POTION and false for HOLOGRAM), so the stale-field bug is
  eliminated at the single decision point.
- **Issue 66 (Omamori underflow):** `BattleContext::exitBattle` guards the
  Omamori decrement with `if (omamori > 0) --omamori;`, matching the existing
  pattern in `Deck.cpp` (curse blocking). A 0-charge Omamori no longer goes to
  −1 and silently skips the Parasite block.
- **Issue 69 (Smoke Bomb no-op):** `BattleContext::drinkPotion` refuses to
  consume a Smoke Bomb in combat: it prints a `std::cerr` warning and returns
  before `discardPotion`, so the potion is kept. The switch case is now
  documented as unreachable. **Open question:** both searchers still enumerate
  the Smoke Bomb use action (`potionRequiresTarget(SMOKE_BOMB)==false`,
  `Action.cpp`, `BattleScumSearcher2.cpp`, `BattleScumSearcher3.cpp`), so
  search simulation budget can still be spent on the refused action; a future
  change could exclude it from enumeration the way FAIRY_POTION is excluded.

## Rationale

- #56: the `cardSelectTask` field is never reset after a select resolves
  (`CardSelectInfo.h`), so after any prior card select the task is stale and
  both failure modes in the issue (missed zero-cost, wrongly zero-costed
  Hologram pickup) occur. The parameter is the only correct signal.
- #66: the bit `hasRelic` is set regardless of charge count, so the decrement
  must be guarded; the reference pattern already exists in `Deck.cpp`.
- #69: the real game forbids using Smoke Bomb in combat; implementing an
  actual flee (end combat) would require touching the battle-outcome state
  machine and searcher semantics, which the plan scoped out. The guard is the
  minimum fix that stops the silent potion waste. **Inference:** a warn-and-
  keep guard is behavior-preserving except for the previously-wasted potion.

## Alternatives considered

- Implement Smoke Bomb as "end combat immediately" (flee) — rejected for now:
  no existing combat-ending potion pattern (Fear Potion is a vuln debuff, not
  a flee) and the real game forbids the use anyway; revisit only if a flee
  mechanic is wanted deliberately.
- Exclude SMOKE_BOMB from searcher enumeration like FAIRY_POTION — deferred:
  plan scoped the fix to the `drinkPotion` guard; the searcher files carry
  unrelated in-progress working-tree changes, and a no-op refused action is
  harmless to correctness, only to search budget.

## Addendum (same session) — guard-only fix stalled the search; searchers now exclude Smoke Bomb

- The guard-only minimum was **insufficient**: with the Smoke Bomb still
  enumerated by the searchers, `./build/one_combat bestbench 10 4 0` printed
  ~38,000 `Smoke Bomb cannot be used in combat` warnings per run and the
  non-fair S2 battle loop hit the `[battle-stall]` 1000-decision guard
  (`ScumSearchAgent2.cpp::playoutBattle`) every run — the refused action is a
  pure no-op, so the search repeatedly re-picks it without state change.
  Reverting only the guard eliminated the stall (0/2 runs), proving causality.
- **Decision:** complete the "forbid its use in combat" direction from issue
  69 by excluding SMOKE_BOMB from potion-action enumeration exactly like
  FAIRY_POTION (the codebase's documented precedent for no-op potion actions):
  `Action.cpp::isValidPotionAction`, `BattleScumSearcher2.cpp::enumeratePotionActions`,
  `BattleScumSearcher3.cpp::enumerateActionsForNode` (potion loop),
  `SimpleAgent.cpp::playPotion` canDrink, `BattleSimulator.cpp::printPotionActions`,
  and `apps/test.cpp::playerNormalGroundTruth` (parity contract). The
  `drinkPotion` guard stays as defense-in-depth for direct/interactive calls
  (the cerr warning now fires only outside search). Verified: 0 warnings, 0
  stalls, `ctest` 21/21, `issue_fixes` PASS, smoke run cpu back to 0.06 s/run.
  **Inference:** the searchers never generate potion-discard actions, so
  excluding Smoke Bomb loses no discard capability the search had.
