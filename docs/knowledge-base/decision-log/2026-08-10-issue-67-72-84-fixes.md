# 2026-08-10 — issues 67, 72, 84 fixed (potion slots, reuse counter, bottled logic)

Date: 2026-08-10
Session/task: Investigator-audit bug-fix pass (issues 67, 72, 84)

## Decisions

### Issue 67 — default potion slots are now EMPTY_POTION_SLOT

- `std::array<Potion, 5> potions` in `include/game/GameContext.h` and
  `include/combat/BattleContext.h` now defaults every slot to
  `Potion::EMPTY_POTION_SLOT` via a member initializer, instead of leaving
  `Potion::INVALID` (0) in default-constructed contexts.
- `BattleContext::init` already copies `potions = gc.potions`, so properly
  initialized contexts are byte-identical before/after; the fix only covers
  default-constructed contexts and `initFromSave` slots beyond the save's
  potion vector (`src/game/GameContext.cpp::initFromSave`, `s.potions` is a
  variable-length vector).

### Issue 72 — `STS_REUSE_ALWAYS_Q` is live

- Chose to implement the counter rather than remove the feature: the flag,
  `g_reuseAlwaysQ`, and the two PUCT exploit-mode reads are a designed,
  opt-in feature (`include/sim/search/BattleScumSearcher3.h:336-338`,
  `src/sim/search/BattleScumSearcher3.cpp:2137,2172`).
- `BattleScumSearcher3::advanceRoot` resets `reuseSearchCount = 0` when the
  tree is promoted (`reused == true`); `search()` and `searchToTotal()`
  increment it when `>= 0`, matching the field comment ("promoted, searches
  executed since last promotion"). The exploit condition
  `reuseSearchCount >= 0` is therefore true on carried trees and Q is used
  from the first carried search onward.
- `parentChildViolations` is left untouched: it is a diagnostic counter with
  no invariant-check site, so there is nothing to increment yet.

### Issue 84 — `Deck::anyCardBottled` fixed, deviating from the plan's `||` → `&&`

- The plan prescribed changing `||` to `&&` so the function "returns true only
  if all three bottles are set". Repository evidence contradicts that:
  - The only call site (`src/game/Deck.cpp:254`) requires `!anyCardBottled()`
    to be true exactly when no card is bottled, because the "simple remove"
    path (`fixed_list::remove`) shifts cards without adjusting `bottleIdxs`.
  - The plan's stated semantic (all three slots filled) makes the simple path
    run with 1–2 bottled cards, silently corrupting `bottleIdxs` on the common
    path (remove any card at or below a bottled card's index).
  - The function name and its sibling `isCardBottled` both mean "any bottle".
  - The reference game's `hasAnyBottledCard` is the any-slot-active predicate.
- Implemented instead: `bottleIdxs[i] != -1` for any i (`||`). This is the
  logical negation of the current `== -1 ||` expression and fixes the only
  genuinely wrong case of the old code (a removal while all three bottles are
  active took the simple path and corrupted `bottleIdxs`); the 0/1/2-bottle
  behaviors are unchanged.

## Rationale

- **Inference (84):** the shift path adjusts `bottleIdxs` for the card shift;
  the simple path does not, so the shortcut is only sound with zero bottled
  cards. Any predicate that is false with 1–2 bottled cards is unsound.
- **Inference (72):** the counter semantics in the header comment are
  self-consistent with a promotion reset plus per-search increment; the
  functional requirement (exploit mode on carried trees) is met by the
  promotion reset alone, and the per-search increment makes the `[reuse-diag]`
  `searches=` field meaningful.

## Alternatives considered

- Removing the `STS_REUSE_ALWAYS_Q` parsing and flag as unimplemented
  (plan's fallback option): rejected — the feature is designed, opt-in, and
  now exercised by a regression test; deleting it would lose the capability
  without a reason.
- Incrementing `reuseSearchCount` at the read sites
  (`selectBestEdgePUCT`/`selectBestValidEdgePUCT`): rejected — those run
  per-edge, per-iteration during selection, so a counter there would not
  measure searches and would add noise.
- Issue 84 `&&` with `== -1` ("all slots empty") and `&&` with `!= -1` ("all
  three filled", the plan's prose): both rejected as unsound at the call site
  (see Rationale).
